## 一、核心结论

统一使用以下最小模板：

```text
日期_标题[_版本].扩展名
```

其中：

- `日期`和`标题`必须存在。
- `版本`仅在确实需要同时保留多个版本时使用。
- `_`只用来分隔日期、标题和版本，不在标题内部使用。
- 中文标题自然书写；英文标题推荐使用小写字母，并以`-`连接单词。
- 不因为已有标题包含大写字母而强制改名。
- 程序项目及其文件不执行本标准，也不由 AI 自动重命名。

标准示例：

```text
20260102_讨论API和ROS2.md
20260123_robot-sourcing-plan.md
20260102_讨论API和ROS2_v1.2.md
2025_公司年度报告.pdf
202508_机器人行业月报.xlsx
2025Q3_季度经营报告.pdf
```

## 二、日期规则

### 2.1 日期表示什么

文件名中的日期优先表示**主要内容日期**，最后修改日期不是默认依据。

如果正文、正式元数据、原文件名和可靠上下文都无法提供内容日期，可以把 Office/PDF 内部创建或最后保存时间、Windows 最后修改时间、创建时间或首次收录时间作为低可信度的**推定日期**。推定日期表示当前归档版本的形成或收录时间，必须在预览中说明依据。

无论日期来自正文还是推定，一旦写入文件名，后续普通编辑不再跟随最后修改时间反复改名。

### 2.2 日期精度

按内容实际需要选择最合适的精度：

```text
YYYY       年，例如 2025
YYYYMM     月，例如 202508
YYYYMMDD   日，例如 20260102
YYYYQ1     第一季度
YYYYQ2     第二季度
YYYYQ3     第三季度
YYYYQ4     第四季度
YYYY-YYYY                 跨年范围，例如 2021-2022
YYYYMM-YYYYMM             跨月范围，例如 202110-202205
YYYYMMDD-YYYYMMDD         精确日期范围，例如 20211001-20220504
```

不要为了凑齐八位数字而虚构月份或日期。

银行流水、对账单和跨期报告有明确起止期间时，日期字段使用与正文精度一致的范围。范围仍属于一个日期字段，只在日期与标题之间使用下划线：

```text
20211001-20220504_示例银行人民币交易流水-账户0000-批次00000000000000.xlsx
```

### 2.3 不同文件采用哪个日期

| 文件类型 | 采用的主要内容日期 |
|---|---|
| 年报、月报、季度报告 | 报告覆盖的时期 |
| 会议纪要、活动资料、照片、录音、视频 | 事件发生或拍摄日期 |
| 合同、发票、证书、正式函件 | 正式签署、签发或开具日期 |
| 公开报告、论文、说明书 | 正式发布日期 |
| 自己创作的笔记、方案、文章 | 首次形成实质内容的日期 |
| 下载或收集但无法判断原始日期的资料 | 首次收录日期，并在 AI 报告中注明“日期为推定值” |

日期证据固定按以下顺序选择，只有上一级缺失时才使用下一级：

```text
正文或正式签发、发生、覆盖日期
→ Office/PDF 内部创建或最后保存时间
→ 原文件名中的期间与可靠上下文组合
→ Windows 最后修改时间
→ Windows 创建时间或首次收录时间
```

补充规则：

- 人工资料只要能从上述证据链得到合理日期，就不因为可信度较低而留下无日期名称。
- 正文只写“7—11月”、内部元数据显示文件形成于2022年时，可以提出`202207-202211_标题.xlsx`，日期可信度为中，并注明年份来自内部元数据。
- 如果大量文件具有完全相同的创建时间，应视为复制、云盘迁移或批量导入信号；该创建时间降级，不直接作为内容日期。
- 最后修改时间与文件内容、原名期间或相邻档案明显冲突时不得采用。
- 所有证据都缺失或冲突无法解释时，保持原名并请求用户决定，不虚构日期。

对于自己创建、下载或收录的文件，日历日期采用中国标准时间（`Asia/Shanghai`）。有明确发生地或发布日期的外部材料，采用材料本身对应的当地日历日期。

### 2.4 不纳入人工重命名的时间戳文件

日志、监控记录、缓存、自动备份及其他机器自动生成的时间戳文件，不使用本规范重命名。它们继续遵守生成软件自己的规则。

## 三、标题规则

### 3.1 中文标题

中文自然连续书写，不在每个词之间插入符号：

```text
20260102_机器人出口合规清单.md
```

### 3.2 英文标题

新建英文标题时，推荐使用小写字母，并以半角横线`-`连接单词：

```text
20260123_robot-sourcing-plan.md
```

已有大写字母、品牌名称或缩写可以保留，不必只为统一大小写而改名：

```text
20260102_讨论API和ROS2.md
20260102_OpenAI-API-guide.md
```

但是，不得只靠大小写区分两个文件：

```text
report.pdf
Report.pdf
```

Windows 通常不区分文件名大小写，Linux 通常区分。只靠大小写区分可能导致跨系统复制、同步或解压时发生冲突。

### 3.3 中英混合标题

- 中文部分自然书写。
- 英文词组内部可以使用`-`。
- 常见缩写和产品名称可以保留原有写法。
- 标题必须让人能从名称判断文件内容，避免`资料`、`文件1`、`新建文档`等空泛名称。

### 3.4 `_`与`-`的职责

两种符号分工固定：

```text
_  分隔日期、标题、版本
-  连接英文单词，或在标题内部作必要的简短连接
```

推荐：

```text
20260123_robot-sourcing-plan_v1.2.md
```

不推荐：

```text
20260123_robot_sourcing_plan_v1.2.md
```

第二种写法会让 AI 难以判断哪些内容属于标题、哪些内容属于版本或其他字段。

### 3.5 核心识别词与稳定编号

人工长期归档的电子发票、银行流水、账户对账单、缴税凭证和政府回执，标题必须同时满足：

```text
主体或来源 + 用途 + 核心识别词（pillar word） + 稳定官方编号
```

核心识别词是让人一眼判断档案类型的描述性文字，例如：

```text
咨询服务费发票
酒店住宿费发票
人民币交易流水
账户对账单
缴税凭证
业务回执
```

稳定官方编号按材料类型选择：

- 发票优先保留发票号码；订单发票可在必要时保留订单号。
- 单笔银行回单优先保留交易流水号；批量流水或对账单优先保留对账单号、导出批次号，并可补充账户尾号四位。
- 政府回执、缴税凭证和申报材料优先保留回执号、凭证号或业务编号。
- 不把完整银行卡号、完整银行账号、校验码、二维码密文或纳税人识别号写入文件名；银行账号只保留尾号四位。
- 正文没有稳定编号时不虚构编号；使用可读标题，并在整理记录中保留原文件名。

稳定编号属于标题内部，用半角横线连接，不新增下划线字段：

以下主体与编号均为虚构示例：

```text
20230109_示例甲方咨询服务费发票-00000001.pdf
20240924_示例酒店住宿费发票-00000002.pdf
20211001-20220504_示例银行人民币交易流水-账户0000-批次00000000000000.xlsx
202204_示例银行账户对账单-账户0000-EXAMPLE001.pdf
```

### 3.6 强主体档案必须保留当事人姓名

身份证、护照、户口簿、签证与移民材料、个人简历、收入或在职证明、医疗记录、个人合同、学历证书及已填写的个人申请表等**强主体档案**，标题必须保留经正文、正式元数据、清晰视觉证据或原文件名确认的当事人姓名：

```text
日期_主体姓名+档案类型[-用途或稳定编号].扩展名
```

以下姓名与编号均为虚构示例：

```text
20260811_示例甲居民身份证扫描件.pdf
202503_示例乙收入证明-签证材料.pdf
2024_示例丙英文简历.pdf
```

- 所选根目录或父文件夹的所有者不等于文件主体；不得仅根据所选根目录或父文件夹推定主体，也不得因为文件已放在个人目录中而省略姓名。
- 同一文件涉及多人时，保留主要当事人姓名或足以区分各方的关系与用途；不能确认主要主体时标为待确认。
- 空白模板不添加姓名；只有证据表明表格或文档已属于具体个人时才添加。
- 主体无法确认时，保留原名中的可靠主体线索或标为待确认，不把目录所有者姓名机械写入全部文件。

### 3.7 含糊名称必须读取内容

`Untitled`、`文件1`、纯编码、`员工成本`等无法让人判断对象或用途的人工资料，在本地可安全读取时，必须先检查必要正文、首页、工作表标题或正式元数据，再提出描述性标题。日期、对象和用途已经清楚的文件不为重复确认而全文读取。

## 四、版本规则

版本字段是可选字段。只有确实需要让多个版本同时存在时才添加：

```text
20260102_机器人出口方案_v1.0.docx
20260102_机器人出口方案_v1.1.docx
20260102_机器人出口方案_v2.0.docx
```

规则：

- 版本使用`v主版本.次版本`，例如`v1.0`、`v1.2`、`v2.0`。
- 版本始终位于标题之后、扩展名之前。
- 如果只是持续编辑同一份工作文件，不增加版本号。
- 不使用`final`、`最终版`、`真的最终版`、`最新版`、`new`、`copy`等不稳定表述。
- 某类文件以后形成稳定的系统化需求时，再为该类文件单独制定专项规则；不要扩张本通用模板。

## 五、字符与扩展名规则

### 5.1 推荐字符

新文件名原则上只使用：

- 中文及其他正常 Unicode 文字；
- 英文字母；
- 阿拉伯数字；
- 半角下划线`_`；
- 半角横线`-`；
- 版本号和扩展名中的半角点`.`。

### 5.2 避免使用的字符

以下字符可能被 Windows、OneDrive、SharePoint、PowerShell、URL、压缩软件或自动化脚本解释为特殊字符，新的通用文件名中不使用：

```text
< > : " / \ | ? * # % & ; , ' ` [ ] { } ( )
```

同时避免：

- 半角或全角空格；
- emoji；
- 换行、制表符和不可见字符；
- 文件名开头或结尾的空格；
- 文件名结尾的点；
- 仅由标点符号构成的标题。

方括号`[]`虽然能出现在部分系统的文件名中，但在 PowerShell 中属于通配符语法，因此不作为长期通用标准。

特殊技术词建议转写：

```text
C++     → cpp
C#      → csharp
.NET    → dotnet
R&D     → r-and-d
Node.js → nodejs
```

### 5.3 Windows 保留名称

不得将以下名称单独作为文件标题或完整文件名，无论扩展名是什么：

```text
CON PRN AUX NUL
COM0 至 COM9
LPT0 至 LPT9
desktop.ini
```

同时避开以`~$`开头的名称，因为 Office 常用它创建临时锁文件。

### 5.4 扩展名

- 新文件扩展名推荐小写，例如`.pdf`、`.docx`、`.jpg`。
- 已有大写扩展名不作为单独改名理由。
- 不通过改扩展名转换文件格式。
- `.tar.gz`、`.nii.gz`等应识别为完整复合扩展名。
- 扩展名缺失、格式与扩展名不符或真实格式无法确认时，只报告，不猜测修改。

## 六、长度与目录规则

为了兼容 Windows 文件资源管理器、Office 桌面软件、OneDrive、SharePoint、压缩软件及较旧程序，采用以下保守限制：

- 完整文件名（包含扩展名）建议不超过 100 个字符。
- 完整绝对路径建议不超过 240 个字符。
- 文件夹通常不超过 5 层。
- 超限时精简标题，不截断日期、扩展名和版本。
- AI 不得机械截断标题，必须提出仍能表达内容的短标题。

文件夹采用独立规则：

- 长期分类目录不强制添加日期。
- 只有明确的项目、活动或批次目录才添加年、月或日。
- 文件夹也遵守安全字符和路径长度规则。

示例：

```text
业务资料
业务资料\客户\示例客户
202608_示例行业展
20260812_示例交付批次
```

## 七、适用范围与禁止范围

### 7.1 可以整理的人工资料

- Word、Excel、PowerPoint、PDF 等办公文件；
- 人工管理和归档的图片、音频、视频；
- 下载并归档的报告、合同、说明书、论文和研究资料；
- 个人笔记；
- 非程序项目中的 Markdown 文件；
- 用户在本次操作中明确指定的其他普通资料。

这里的“人工资料”是指主要供人阅读、管理和归档的文件，不要求必须由用户亲手创建。

### 7.2 整个程序项目默认禁止重命名

只要目录中发现`.git`、`package.json`、`pyproject.toml`、`Cargo.toml`、`go.mod`、`.sln`等程序项目标志，默认跳过整个项目目录，而不是只跳过源码扩展名。

禁止自动重命名的内容包括但不限于：

- 源码、测试、脚本和配置；
- 数据库、迁移文件、模型权重；
- 网页图片、字体和其他可能被代码引用的资源；
- 锁文件、构建文件和依赖文件；
- `README.md`、`LICENSE`、`.gitignore`等固定名称文件；
- 任何可能被框架、构建工具或部署流程依赖的文件。

只有用户明确指定某个普通资料目录，并确认它不受程序引用时，才可以把该目录纳入整理。

### 7.3 其他默认禁止处理的文件

- 系统文件、隐藏文件、缓存和临时文件；
- 日志、监控记录、自动备份和其他机器生成文件；
- 应用数据库、邮件数据库和同步软件的内部文件；
- 快捷方式、符号链接、目录连接和挂载点；
- 未完整下载的云盘占位文件；
- 必须保持成套关系的交付材料；
- 用户没有选入本次范围的文件和目录。

普通压缩包本身可以作为普通文件提出改名建议，但 AI 不自动解压、修改或重新打包其中的内容。

已完整下载、由人工长期归档的独立电子发票、银行流水、对账单、缴税凭证或政府回执，在正文可读且不存在导入依赖、外部引用、数字签名交付约定或同步异常时，可以同时分类和重命名。新名称必须包含可读的核心识别词，并尽量保留稳定官方编号；整理记录必须保存原文件名与最终文件名。

### 7.4 签名或加密 PDF：内容保护与外层路径分开判断

嵌入式数字签名和加密保护 PDF 的字节、内容和权限，不天然保护操作系统中的外层文件名。独立 PDF 只有同时满足下列条件，才可提出**仅文件系统**的改名或移动：文件已完整本地下载；身份、日期和标题可确立；不改写 PDF 字节；未发现清单、导入/验真键、外置 detached signature、成套交付约定、共享路径或其他文件名/路径依赖；目标无冲突。

任一条件未核实就保持原位并标明缺口。组织过程严禁打开后保存、解密后保存、OCR 替换 PDF、压缩、元数据编辑、打印为 PDF、签名修改或任何内容重写。获批执行时必须保存原路径回滚映射，逐份记录前置 SHA-256、签名指示器和加密状态，并在改名/移动后复核 SHA-256 完全相同、签名指示器及加密状态未变。

如果原文件名是后续导入、验真、对账、外部提交或系统调用的必要键，保持原名，只提出分类移动并醒目标注原因。软件内部运行文件、日志、缓存和自动备份仍不纳入人工重命名。

## 八、重复文件规则

“文件名相同”不等于“内容相同”，“看起来相同”也不等于“可以安全删除”。

### 8.1 确定重复

先按文件大小分组。大小不同的文件不可能二进制完全相同；只有同尺寸的重复候选才计算内容哈希。哈希相同才列为“确定重复候选”。

即使确定重复，AI 也只能提出：

- 建议保留哪个文件；
- 建议删除哪个文件；
- 保留与删除的理由；
- 是否存在链接、共享、同步或路径风险。

删除仍属于独立的破坏性操作，必须在重命名之外再次获得用户明确确认。

### 8.2 疑似重复

以下情况只能列为“疑似重复”，不得自动删除：

- 内容看起来相同但哈希不同；
- 同一 PDF 由不同软件生成，元数据不同；
- Word 与 PDF；
- 原图与压缩图；
- 可编辑源文件与导出文件；
- 不同清晰度、码率、分辨率或文件格式的媒体；
- 同名但内容不同的文件。

同名但内容不同的文件，应增加有意义的标题信息，而不是使用`(1)`、`副本`或`copy`。

## 九、跨平台兼容性风险清单

AI 在提出批量改名建议时，必须检查以下风险：

1. **Windows 非法字符和保留名称**：可能导致无法创建、复制、同步或删除。
2. **PowerShell 通配符**：`[]`、`*`、`?`等可能被当成匹配表达式。
3. **Windows 与 Linux 大小写差异**：Linux 可能把两个名称视为不同文件，Windows 可能视为同一文件。
4. **Unicode 表达差异**：肉眼相同的字符可能有不同底层编码。比较和生成名称时使用 Unicode NFC；发现冲突先报告。
5. **全角与半角字符**：全角字母、数字、横线和空格可能导致搜索、排序及脚本判断不一致。
6. **路径长度**：深层目录和长标题可能在云端可见，却无法在 Windows 或 Office 桌面程序中打开。
7. **云盘同步**：OneDrive、SharePoint 或其他云盘可能正在同步、存在占位文件或产生重名冲突。
8. **共享链接变化**：文件改名后，旧的共享链接、收藏记录或外部引用可能失效。
9. **Obsidian 和 Markdown 链接**：改名可能影响 Wiki 链接、Markdown 链接、嵌入和附件引用。
10. **Office 外部链接**：Excel、Word、PowerPoint 可能引用其他文件或资源。
11. **快捷方式和第三方数据库**：软件可能按原路径记录文件，单纯改名不会自动更新所有引用。
12. **Git 与程序项目**：改名可能破坏导入、路由、构建、测试、部署或历史追踪，因此整项目默认跳过。
13. **压缩包**：压缩包内文件属于独立命名空间，不自动进入整理范围。
14. **数字签名、加密与成套交付**：虽然改外部文件名不一定改变文件内容，但仍须逐项核实交付约定、清单关系或外部验证流程；独立 PDF 仅可按 7.4 的全部条件进行外层改名/移动。
15. **文件扩展名**：错误修改扩展名不会转换格式，反而可能导致软件无法打开文件。
16. **同步中的大小写改名**：仅修改大小写可能无法被部分系统正确识别，本规范不为大小写单独改名。
17. **同名覆盖**：任何目标名称已存在时必须停止，不允许静默覆盖。

## 十、AI 整理文件名的标准流程

### 第一步：确认范围

- 只处理用户在本次调用中明确选择的文件或目录。
- 未明确范围时先询问，不扫描整台电脑、整个云盘或整个知识库。
- 目录可以递归扫描子目录，但不得跨越快捷方式、符号链接、目录连接、挂载点或范围外路径。
- 每次都由用户主动调用，不建立自动持续监控。

### 第二步：只读扫描和识别

AI 先识别：

- 可整理的普通人工资料；
- 程序项目及受保护目录；
- 系统、隐藏、机器生成或特殊文件；
- 确定重复候选和疑似重复候选；
- 可能存在引用、同步、签名、加密或路径风险的文件。

这一阶段不得改名、移动或删除任何文件。

例外：`.DS_Store`、`._*`和经占用检查确认安全的`~$*`按《自动清理生成元数据规则》和本次冻结的有效策略处理；公开默认策略只预览，只有显式选择自动清理预设时才删除。字体和其他资产本体必须保留。

### 第三步：生成操作预览

只重命名模式对所有拟改名和日期未决文件提供如下映射表：

| 原文件名 | 建议文件名 | 日期依据 | 日期可信度 | 建议动作 | 风险或说明 |
|---|---|---|---|---|---|
| 示例.pdf | 2025_公司年度报告.pdf | 报告覆盖年度 | 高 | 仅改名 | 无已知风险 |

同时分类并重命名时，使用《通用文件分类标准》规定的综合预览字段，并明确展示原路径、建议文件名和最终路径。清楚的`保持不变`、程序项目和机器文件按数量与理由汇总，不逐项生成冗长记录。

日期可信度可以使用：

- 高：文件正文或正式元数据显示明确日期；
- 中：可由可靠上下文推断；
- 低：只能使用可靠的内部形成时间、最后修改时间、创建时间或首次收录时间，必须注明“推定日期”。

### 第四步：等待确认

- 用户确认具体映射表后，AI 才能执行所批准的动作。
- 只重命名预览的批准只授权改名，不授权移动。
- 综合预览中，用户明确批准一条具体最终路径，即授权该条列明的必要新建文件夹、移动和改名。
- 修改引用、操作整个现有文件夹、移动到所选根目录之外，仍需单独明确授权。
- 用户确认重命名不等于确认删除重复文件。
- 删除重复文件必须单独列出并再次获得明确确认。

### 第五步：执行批准的最终路径

- 只执行用户确认的映射。
- 不扩大范围，不顺手整理其他目录。
- 不覆盖已有文件。
- 不改变文件内容和真实格式。
- 只重命名模式保留原目录；综合模式直接从原路径移动到已批准的最终路径，避免先改名再移动的中间状态。
- 不操作整个现有目录，除非用户另行明确授权。
- 遇到新发现的程序项目、链接风险、同步异常或重名冲突时，停止相关文件并报告。

### 第六步：验证与完成度审计

AI 只有在以下检查通过后，才能说“整理完成”：

- 执行前后文件总数符合预期；
- 普通同根目录改名或移动核对路径、大小和最后修改时间；只有重复确认、受保护文件、跨存储复制、异常或明确审计要求才进行针对性内容哈希；
- 没有文件丢失、覆盖或意外移动；
- 没有未处理的重名和大小写冲突；
- 文件名和完整路径未超出本规范建议长度；
- 可识别的 Obsidian、Markdown、Office 和其他引用已经检查；
- 云盘同步完成且没有明显报错；
- 已保存“旧路径 → 最终路径”映射。

最后再做一次轻量检查：是否仍有可确定日期却未加日期的人工文件、`Untitled`或空泛标题、未处理目标冲突、明显错误分类、根目录散文件和空目录。空目录只报告，未获单独授权不删除。

### 第七步：保留回滚能力

每次执行后保留反向映射：

```text
最终路径 → 原路径
```

如果发现链接、同步或软件兼容问题，可以按映射恢复原名。回滚同样不得覆盖现有文件。

## 十一、可直接交给 AI 的通用指令

以下内容可以跨电脑、跨项目直接使用，只需在调用时选定要处理的文件或目录：

```text
请按照《通用文件命名标准》检查我本次明确选择的文件或目录。

统一模板为：日期_标题[_版本].扩展名。

这是只重命名模式。请先只读扫描，不要改名、移动或删除文件。保持所有文件所在目录不变，对拟改名和日期未决文件输出“原文件名、建议文件名、日期依据、日期可信度、建议动作、风险或说明”，其余文件按数量和理由汇总，等待我确认后再执行。

日期优先使用主要内容日期。正文日期缺失时，按“内部创建/保存时间 → 原名期间与可靠上下文 → 最后修改时间 → 创建或首次收录时间”逐级使用推定日期，并注明可信度；名称确定后不随以后修改反复变化。日期精度允许 YYYY、YYYYMM、YYYYMMDD、YYYYQ1 至 YYYYQ4。中文标题自然书写；英文新标题推荐全小写并用半角横线连接。已有大写、品牌或缩写不为大小写单独改名。下划线只分隔日期、标题和可选版本。身份证、护照、简历、收入证明等强主体档案必须保留经证据确认的当事人姓名；不得根据个人目录的所有者猜测主体，空白模板不添加姓名。

只处理本次选择范围。发现程序项目时跳过整个项目目录；不要处理源码、配置、测试、依赖、机器生成文件、日志、缓存、备份、隐藏文件、系统文件、符号链接、快捷方式或云盘占位文件。签名或加密的独立 PDF 只能在全部外层路径条件已核实、且不改写任何 PDF 内容时提出改名/移动；否则保持原位并说明缺口。

只有大小相同的重复候选才需要计算内容哈希；哈希完全相同才能列为确定重复候选。删除属于独立操作，即使文件完全重复，也必须再次列出保留项、删除项和理由，获得我的明确确认后才能删除。内容不同但名称相同的文件，应提出有意义的新标题。

执行前检查重名、大小写、非法字符、Unicode、路径长度、云盘同步和链接风险。普通同根目录改名或移动只核对路径、数量、大小和最后修改时间；哈希仅用于重复确认、受保护文件、跨存储复制、异常或明确审计。执行后保存可回滚的旧名称和新名称映射，不得静默覆盖文件，也不得扩大我选择的范围。
```

## 十二、快速自检清单

新建人工资料文件时，只需检查：

- [ ] 日期是否优先使用主要内容日期；使用推定日期时是否标明依据并在命名后冻结？
- [ ] 日期精度是否真实，没有虚构月或日？
- [ ] 是否使用`日期_标题`作为基本结构？
- [ ] `_`是否只用于分隔日期、标题和可选版本？
- [ ] 英文单词是否优先用`-`连接？
- [ ] 标题是否足以说明文件内容？
- [ ] 强主体档案是否保留了经证据确认的当事人姓名，并避免根据父目录猜测主体？
- [ ] 官方归档标题是否包含发票、交易流水、账户对账单、缴税凭证或业务回执等核心识别词？
- [ ] 是否保留了发票号码、流水号、对账单号、回执号或批次号等稳定编号，并避免暴露完整银行账号？
- [ ] 是否避免了危险字符、空格、emoji 和不可见字符？
- [ ] 是否真的需要版本号？
- [ ] 文件名和完整路径是否足够短？
- [ ] 该文件是否属于程序项目或机器生成文件？如果是，不执行本规范。
